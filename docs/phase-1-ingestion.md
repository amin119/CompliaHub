# Phase 1 — Document Ingestion Pipeline

Status: **done**. Upload → dedup → parse → chunk → stored with hierarchy,
end-to-end. Embedding and entity extraction are Phases 2–3, not touched here.

## Goal

Get ISO 42001, ISO 27001, and GDPR source text into structured, hierarchical
chunks with clean metadata — the foundation everything else (vector search,
graph extraction, retrieval) is built on.

## Concepts learned

- **Why fixed-size chunking breaks structured legal/compliance text.** These
  documents have a strict hierarchy (Standard → Part → Clause → Sub-clause →
  Control). Chunking at clause boundaries (not fixed token windows) keeps a
  requirement's text bound to its own clause number, which is what makes exact
  citations possible later.
- **Async job queues and resumability.** Celery + Redis makes each pipeline
  stage (parse, chunk) its own task; a failure in one stage marks the
  document `failed` with a reason instead of losing the whole pipeline run.
- **Idempotent ingestion via content hashing.** SHA-256 of the raw upload is
  the dedup key — re-uploading the same file returns the existing `Document`
  row untouched, no reprocessing. Foundation for Phase 8's incremental
  ingestion.
- **Materialized paths (`ltree`).** Clause numbers already *are* a natural
  path (`A.8.1.2`); Postgres's `ltree` extension turns "everything under Annex
  A.8" into one indexed query (`path <@ 'iso27001.a.8'`) instead of a
  recursive CTE.

## Decisions made

- **Parsing: Docling.** Confirmed working (Step 0 sanity check) — one library
  for both PDF and DOCX, `SectionHeaderItem`/`TextItem` stream from
  `doc.iterate_items()` walks straight into a heading tree. **Gotcha:** the
  install pulled in a much heavier dependency tree than expected —
  `torch`, `torchvision`, `transformers`, `opencv-python`, `rapidocr` — not
  just a lightweight heuristic parser. Accepted as a one-time disk-space cost.
  The DOCX path (native structure, no ML layout model) was verified directly;
  the PDF path (which uses the heavier ML layout model) gets its first real
  test against an actual ISO/GDPR PDF in manual verification, not covered by
  the fixture-based unit tests.
- **Hierarchy: `ltree`.** `Chunk.path` uses `sqlalchemy_utils.LtreeType`,
  with an explicit `CREATE INDEX ... USING GIST` in the migration — a plain
  btree index (SQLAlchemy's default `index=True`) does *not* support the
  `<@`/`@>` operators ltree queries need; that has to be GiST, added by hand.
  `parent_chunk_id` is kept alongside `path` purely for O(1) direct-parent
  lookups — it answers "what's the immediate parent row," which `path` alone
  (a string) can't without another query.
- **Job queue: Celery, worker in Docker.** Confirmed Celery's default worker
  pool needs `os.fork()`, unavailable on native Windows. The worker now runs
  in its own Linux container (`backend/Dockerfile`), while the FastAPI dev
  server still runs natively on the Windows host via `uv run uvicorn`.
  **Container-networking gotcha:** the worker reaches Postgres/Redis/MinIO by
  *service name* (`postgres`, `redis`, `minio`) over the compose network;
  the host-run FastAPI process reaches the same containers via `localhost` +
  published ports. Same services, two different env var sets
  (`backend/.env` for the host process, `environment:` block in
  `docker-compose.yml`'s `worker` service for the container) — not a
  duplication mistake, a real difference in network vantage point.
- **Schema/migrations: SQLAlchemy + Alembic** (decided during planning, not
  discussed beforehand) — standard choice for FastAPI+Postgres over
  hand-written SQL scripts with no migration history.
- **Roadmap deviation:** the roadmap lists a separate `chunk_hierarchy` table;
  consolidated into `path` (ltree) + `parent_chunk_id` directly on `chunks`
  instead, since `ltree` already gives full-subtree query power a join table
  would otherwise exist for.

## Gotchas worth remembering

- **`sqlalchemy_utils.Ltree` isn't a plain string — two bugs from this.**
  (1) *Writing*: `LtreeType`'s bind processor calls `.path` on whatever value
  it's given, so assigning a raw Python `str` to `Chunk.path` crashed with
  `AttributeError: 'str' object has no attribute 'path'` — the value has to
  be wrapped as `Ltree(path_string)` before it's set on the model. (2)
  *Reading*: `Ltree` also isn't a `str` subclass, so returning it straight
  through a Pydantic `path: str` field failed response validation — fixed
  with a `field_validator(mode="before")` that does `str(value)` in
  `ChunkResponse`. Both only surfaced once the integration test ran against
  the real Postgres stack — the pure-function unit tests never touch the
  ORM/DB layer, so they couldn't have caught this. Concrete evidence for why
  the "requires live infra" integration test earns its keep despite being
  skipped in CI.
- **Failure-path bug: `_fail()` needs `db.rollback()` first.** When a flush
  (e.g. the bad `Ltree` insert above) fails mid-transaction, the session's
  transaction is dead; calling `db.commit()` again afterward to record the
  failure raised `PendingRollbackError` instead of cleanly marking the
  document `failed`. Fixed by calling `db.rollback()` at the start of
  `_fail()` before touching any attributes. Worth remembering as a general
  SQLAlchemy pattern: any error-handling path that reuses a session after a
  failed flush must roll back first.
- **Celery chain payload:** `parse_document_task` returns the parsed heading
  tree as a plain dict (`dataclasses.asdict`) so it can travel through the
  Celery chain's JSON-serialized result to `chunk_document_task`. Fine at
  this corpus size; worth revisiting in Phase 8 if a single document's parsed
  tree gets large enough that passing it through the broker/result-backend
  becomes the bottleneck (an intermediate artifact store would be the fix).
- **Testing with `task_always_eager`:** the API integration test runs the
  whole parse→chunk chain synchronously in-process (no live worker needed),
  but this only tests the *happy path* faithfully — a task exception in eager
  mode with `task_eager_propagates=True` raises straight out of the request
  that enqueued it, whereas in real (non-eager) operation the same failure
  happens later in a separate worker process and never reaches the original
  API caller. Don't read too much into eager-mode error behavior matching
  production.
- **`test_documents_api.py` needs live infra** (Postgres with migrations
  applied + MinIO + Redis) — it skips cleanly if unavailable rather than
  failing, so CI (which doesn't run the docker stack) stays green without
  actually exercising this test yet. Something to revisit if/when CI grows a
  services block for integration tests.

## Verification

1. `uv run alembic upgrade head` → confirms tables + `ltree` extension exist
   (`docker compose exec postgres psql -U compliancegraph -d compliancegraph -c '\dt'`).
2. `docker compose up -d --build worker` → `docker compose ps` shows `worker`
   healthy alongside the 5 data services.
3. `uv run uvicorn app.main:app --reload` → `POST /documents` with a real
   ISO/GDPR PDF or DOCX, poll `GET /documents/{id}` until `ready`, then
   `GET /documents/{id}/chunks` to eyeball clause boundaries and paths.
4. Re-upload the same file → same document `id` comes back (dedup works).
5. `uv run pytest` — hashing/chunking/parsing tests always run; the two
   `test_documents_api.py` tests additionally run (not skip) once the stack
   from steps 1–2 is up.

## Refactor: extracted Celery task boilerplate

Done alongside a Phase 2 DIP fix (see `docs/phase-2-vector-layer.md`'s
"Refactor" section for the full rationale). `app/tasks/ingestion.py`'s three
tasks (`parse_document_task`, `chunk_document_task`, `embed_chunks_task`)
each repeated the same skeleton: open a session, load the `Document`,
create+track a `ProcessingJob`, commit, wrap the real work with `_fail()` on
exception, mark the job successful, final commit, close the session — a DRY
violation. Extracted into one `pipeline_stage(document_id, task_name,
in_progress_status)` context manager, yielding `(db, document)`; each task
body now contains only the logic unique to that stage. Preserves the exact
original commit/rollback ordering — a failure before the first commit (e.g.
the document not existing) still isn't caught by `_fail`, matching prior
behavior. Covered by a dedicated `tests/test_pipeline_stage.py` (infra-gated,
same pattern as the other integration tests) in addition to the existing
full-chain test in `test_documents_api.py`, which still passes unchanged —
proving the refactor didn't alter observable behavior.

## What Phase 2 needs from here

The `chunks` table (`text`, `clause_number`, `path`) is Phase 2's entire
input — one row per chunk to embed and store in Qdrant, with `path`/
`clause_number` carried along as metadata for citations. No schema changes to
`chunks` anticipated for Phase 2 itself.
